<lessons_desta_fase>
A verificação manual desta fase encontrou quatro defeitos que TODOS os gates automáticos
deixaram passar. Dois são diretamente relevantes para este plano:

1. **`input.required()` NÃO pode ser lido no constructor.** Os inputs ainda não estão
   populados ali. Ler lança, e se a promise estiver silenciada com `void`, o signal de
   loading nunca volta para `false` e a tela fica presa em "Carregando..." para sempre.
   Usar `effect()`. Padrão concreto a replicar: `join-group.page.ts:35-44` e
   `manage-group.page.ts:76-92` (commit 22fda92).

2. **Um `UrlTree` devolvido por um `ResolveFn` NÃO redireciona.** Diferente de
   `CanActivateFn`, onde é o contrato oficial, o valor de um resolver só vira `route.data`.
   Um não-admin chegou a ABRIR a tela de gestão de grupo alheio por causa disso. **Toda
   checagem de acesso vai em `CanActivateFn`** (commit 22f2181, `admin.guard.ts`).

   O corolário que este plano DEVE respeitar: o spec do resolver passava verde justamente
   porque verificava que ele RETORNAVA um `UrlTree`, nunca que o Router AGIA sobre ele.
   O spec do `memberGuard` precisa provar **navegação real**, não valor de retorno.
</lessons_desta_fase>

<rls_que_torna_isto_possivel>
As policies de SELECT em `group` (migration `0003_rls_policies.sql`) são ORed pela RLS:
admin (`admin_id = auth.uid()`) **ou** membro (`id in (select private.my_group_ids())`).

Consequência que o `memberGuard` explora: `loadGroup(id)` devolve a linha para **admin e
participante igualmente**, e devolve `null` para quem não é nenhum dos dois. O guard não
precisa de query extra em `participant` — "`group` não é null" já significa "sou membro ou
admin". Mesma economia que `adminGuard` faz, sem reintroduzir recursão de policy.

E `refreshParticipants(groupId)` funciona para o participante: a policy
`"participant: ver colegas do mesmo grupo"` usa `private.my_group_ids()`.
</rls_que_torna_isto_possivel>
